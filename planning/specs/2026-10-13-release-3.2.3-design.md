# Release 3.2.3: bug-fix release design

**Date:** 2026-10-13, revised 2026-10-14 for #547 to #554 and the milestone as it stands, revised 2026-10-16 after review
**Status:** Draft; decisions D1 to D11 settled 2026-10-14, D12 to D16 settled 2026-10-16
**Scope:** Fixes that make `prov` accept more valid input or write correct output,
and a `ProvWarning` for every input that 3.3.0 will reject. Nothing that reads
today is rejected. No dependency changes, Python floor unchanged at 3.10.

## 1. Purpose

On 2026-09-30 a comparison of `prov`'s readers against an independent
implementation and the Recommendations filed #508 to #532. The issues were split
the same day between two milestones under a rule set for the 3.2.x line:

> A bug-fix release never rejects what reads today. A 3.2.x fix may only accept
> more valid input or correct writer output. A fix that makes reading stricter
> waits for the next minor release, with a `ProvWarning` in the bug-fix release
> before it.

3.2.3 is that bug-fix release. It has two halves:

- **Fixes** (section 3): the eleven open issues on the 3.2.3 milestone (#510,
  #512, #515, #517, #518, #521, #522, #526, #530, #550, #554). Each one accepts
  input that fails today or corrects output that does not read back. #542
  (Python 3.15 support) is closed and already on `main`; it goes in the 3.2.3
  changelog's Project section.
- **Warnings** (section 4): one `ProvWarning` for each input that 3.3.0 will
  reject, as listed on the milestone (#472, #508, #509, #511, #513, #516, #523,
  #524, #528, #529, #531, #532, the `xsi` half of #510, the `strict` rules of
  #519 and the attribute values of #482). Every one of these inputs reads today
  with no warning at all; the probes behind section 4 confirmed it on `main` at
  797b900.

On 2026-10-14 six more issues were filed from the same kind of review (#547 to
#552), and their milestones were applied the same day (D9). Under the rule, one is a 3.2.3 fix (#550,
section 3.10), three are 3.3.0 rejections that need a 3.2.3 warning first (#547,
#551, #552; sections 4.16 to 4.18), and two are 3.3.0 behaviour changes with no
warning, in the same family as #525 (#548, #549; section 8). All six reproduce on
`main` at 797b900. The same review added two more warnings: model assertion of
an unresolvable qualified-name literal (4.19, from D8) and a malformed bare time
in PROV-JSON (4.20, #555).

3.2.3 is the last release with the 3.10 floor. Python 3.10 reaches end of life
on 2026-10-31, and 3.3.0 raises the floor and turns the warnings into errors, so
3.2.3 should ship before then to give users a release that warns before one that
rejects.

## 2. The warning mechanism

### 2.1 One subclass, one message shape

**Proposal.** Add `prov.model.ProvFutureRejectionWarning(ProvWarning)` and emit
every section 4 warning as that class. A user who wants to check a corpus
against 3.3.0 turns the class into an error (`pytest -W
error::prov.model.ProvFutureRejectionWarning`, a pytest `filterwarnings` entry or
`warnings.simplefilter` in code) and sees exactly what will break, without also failing on the recoverable-input warnings `ProvWarning`
already carries (lenient skips, nested XML references). The name is additive;
`test_public_api.py`'s frozen `dir(prov.model)` gains one entry. 3.2.1 set the
precedent for a small additive name in a bug-fix release.

The alternative is plain `ProvWarning` with a fixed message suffix. It adds no
name but gives callers nothing to filter on except message text. Decision D1.

Every message ends with the same clause, so the warnings read as one family:

```text
line 3, column 1: 'default' is declared twice in this scope; the last one is used. prov 3.3.0 will reject this
```

Reader warnings carry a position where the format has one (PROV-N line and
column; for PROV-JSON, the record identifier and attribute name). Model-API
warnings name the value and the attribute.

The class also carries three inputs that 3.3.0 reads differently rather than
rejects: U+1680 between tokens (4.3), a typed `xsd:dateTime` value with an
offset beyond ±14:00 (4.5) and a Python value 3.3.0 converts (4.15). A
`-W error::` run reports them with the rejections, so their messages name what
3.3.0 does instead ("prov 3.3.0 will read it as a name character", "prov 3.3.0
will keep it as a Literal") and the how-to lists them in their own group.

3.3.0 emits nothing as this class but keeps the name, so a filter that names it
in code or in a pytest configuration keeps working after the upgrade (D14).

### 2.2 Stack level

Every new site uses `external_stacklevel()` (`src/prov/_warnings.py:23`), so a
warning points at the caller's line whether the reader was reached directly or
through `prov.read()`.

### 2.3 PROV-N side channel

The PROV-N parser never calls `warnings.warn` itself: lenient skips go into
`ProvNParser.skipped` and `ProvNSerializer.deserialize` (`provn.py:80-83`) emits
them. The new PROV-N warnings use the same pattern with a second list,
`ProvNParser.warnings`, drained in the same place. The lexer has no channel
today; `_Lexer` gains a list the parser forwards, for #509 only.

### 2.4 Auto-detection must not leak a failed candidate's warnings

`prov.read()` without a format (`_detect_and_parse`, `__init__.py:96-124`)
swallows each failed candidate's exception but not its warnings. Once the JSON
reader warns about repeated keys (#532), a JSON-LD document with a repeated key
would print a PROV-JSON warning from the failed attempt. And under
`-W error::...`, a warning becomes an exception, so detection silently moves on
to the next format instead of reporting it.

**Change.** `prov`'s own warnings go through one helper,
`prov._warnings.warn()`, which every reader and writer calls instead of
`warnings.warn`. Outside auto-detection the helper warns as before, attributed to
the caller's line. During auto-detection, `_detect_and_parse` sets a per-read
collector in a `contextvars.ContextVar` around each candidate, and the helper
appends to it instead of warning. Once a candidate wins, `_detect_and_parse`
emits that candidate's collected warnings with `warnings.warn` at the caller's
line. A failed candidate's collection is dropped, and so is that of a candidate
that parses to an empty document, since detection treats it as not detected.

The collector touches no global warning state. Python's once-per-location record
and the caller's filters behave as on the explicit-format path, and concurrent
reads in threads or tasks keep separate collections. Warnings from other
libraries are not collected, so a candidate that `prov` set aside can still show
an rdflib or lxml warning, as it does today. `warnings.catch_warnings` was
rejected for this, because it resets the once-per-location record across the
whole process on every attempt (decision D16).

`test_read.py` gains a test for each case: a failed candidate, an empty
candidate, the winner's warning emitted once at the caller's line, a run under an
`error` filter, a filter scoped to the caller's module, and a warning shown once
per location before a read that does not appear again after it.

### 2.5 Documentation

A new section in `docs/howto/` (or the existing reading how-to), "Preparing for
3.3.0", lists every warning, the input that triggers it and what to write
instead, and shows how to turn the class into an error with pytest or in code.
Python's own `-W` option and `PYTHONWARNINGS` cannot name the class, because
Python reads them before it can import `prov`. The 3.3.0 changelog links to it.

The page also covers two cases that come from `prov` itself rather than from
hand-written input:

- PROV-N files written by `prov` 3.2.2 or earlier that use `xsi:` names have no
  `prefix xsi` line (4.13). Reading and writing them again with 3.2.3 adds it.
- `prov_to_graph` and `prov_to_dot` call `unified()`, so the 4.16 warning fires
  when such a document is rendered. In 3.3.0 `prov_to_graph` raises and
  `prov_to_dot` falls back to the bundle as asserted.

## 3. Fixes

Each item names the current behaviour, the change and the tests. Every item
gets a changelog line under `## 3.2.3`. Reproducers were re-run on 797b900; all
nine filed before 2026-10-14 still fail as filed.

### 3.1 PROV-N reader: `xsi` is an ordinary prefix (#510, first half)

**Now.** `prefix xsi <...>` raises "prefix 'xsi' is reserved", because
`_check_reserved_prefix` (`provn_parser.py:303-310`) checks against all of
`DEFAULT_NAMESPACES` (prov, xsd and xsi). PROV-N reserves only `prov` and `xsd`.

**Change.** The reserved set is `prov` and `xsd`. A document may declare `xsi`
to any IRI.

Removing the check is not enough. `NamespaceManager.add_namespace` renames a
clashing prefix to `xsi_1`, and `_resolve_prefixed_string`
(`namespaces.py:289-297`) checks the built-in `xsi` before the renamed map, so
`xsi:e` would resolve against the wrong IRI. The parser resolves `xsi:` against
the document's own declaration at document and bundle scope.

The PROV-N writer emits `xsi:type` names with no `prefix xsi` line. That output
reads today but would warn under section 4.13 and fail in 3.3.0, so the writer
declares `xsi` whenever it uses it. That is an output correction and fits the
rule.

**Tests.** `test_provn.py`: `prefix xsi <http://other/>` with `xsi:e` resolves to
the declared IRI, at document and bundle scope; the writer's output for an
`xsi:type` attribute contains the declaration and reads back with no warning.
`test_prefix_declaration_rejects_redeclaring_a_reserved_prefix` (line 377)
switches from `xsi` to `xsd`.

The issue moves to the 3.3.0 milestone once this and section 4.13 land.

### 3.2 PROV-N reader: an empty namespace IRI is a syntax error (#512)

**Now.** `prefix z <>` and `default <>` raise a bare `ValueError` from
`Namespace.__init__` (`identifier.py:383`), under every profile including
`lenient`, because declarations sit outside the statement `try`.

**Change.** `_declarations` (`provn_parser.py:270-301`) raises
`ProvNSyntaxError` at the IRI token for an empty IRI, in both branches and at
bundle scope. The input fails today and still fails; only the exception type
and position change. Under `lenient` it stays an error, since a declaration is
not a statement that can be skipped. `ProvNSyntaxError` derives from
`ProvException`, not `ValueError`, so a caller that catches `ValueError` around
such a document stops catching it. The changelog line says so.

**Tests.** `test_provn.py`, beside the declaration tests: both forms, document
and bundle scope, all three profiles, assert the type and the position.

### 3.3 `prov:time` accepts an `xsd:dateTime` literal (#515)

**Now.** `[prov:time="2012-01-01T00:00:00" %% xsd:dateTime]` fails with
`Invalid value for attribute prov:time`, and so does
`wasGeneratedBy(..., time=Literal(..., XSD_DATETIME))` from code.

**Change.** In `ProvRecord._coerce_attribute_value` (`records.py:913-920`), a
`Literal` typed `xsd:dateTime` in a `PROV_ATTRIBUTE_LITERALS` slot is parsed with
`parse_xsd_datetime`. A bad lexical form still raises there: the slot needs a
datetime, unlike an ordinary attribute (section 3.7).

The PROV-JSON reader has the same gap with a different symptom (#554):
`"prov:time": {"$": "...", "type": "xsd:dateTime"}` crashes with
`AttributeError: 'dict' object has no attribute 'strip'` from
`_decode_formal_attribute` (`provjson.py:571`). An activity's `prov:startTime`
and `prov:endTime` crash the same way (probe on 14f5308).
`_decode_formal_attribute` unwraps a value object typed `xsd:dateTime` and
parses its text, for all three time attributes. As #554 asks, a value object with a malformed lexical
form or another datatype raises `ProvJSONException` naming the attribute and the
value. Both fail with `AttributeError` today, so this changes only the exception
and adds no rejection.

The bare-string form is inconsistent with that. `"prov:time": "not-a-time"`
reads today and the time is silently dropped: the record comes out as
`wasGeneratedBy(ex:g; ex:e, -, -)` (probe on 797b900). Rejecting it is a 3.3.0
change, so 3.2.3 warns there (section 4.20, #555).

**Tests.** `test_datetime_parsing.py` for the model call (`test_attribute_typing.py`
holds static-typing assertions only); `test_provn.py` and
`test_json.py` for the readers, including #554's reproduction on every relation
with a time and on an activity's start and end times; a bad lexical form and a non-`xsd:dateTime` value object raise
`ProvJSONException`.

### 3.4 PROV-JSON writer: a default-namespace name containing `:` (#517)

**Now.** With `default <http://d.example/>`, the name `a\:b` is written as the
key `"a:b"`, which reads back as prefix `a`. The round trip fails with
`ProvElementIdentifierRequired`. PROV-JSONLD has the same defect (verified).

**Change.** `encode_json_container` (`provjson.py:206-278`) writes such a name
with a prefix bound to the default namespace IRI, declaring one if the document
has none. The rewrite applies at every qualified-name emission site: record
identifiers, attribute names, formal values, `xsd:QName` values
(`encode_json_representation`) and bundle identifiers. One helper builds a
JSON-specific prefix map and serves #518 too. The PROV-JSONLD writer uses the
same helper.

**Tests.** In the shared `test_qnames.py`, so JSON and JSON-LD are both covered:
a default-namespace local part with `:` round-trips.

### 3.5 PROV-JSON writer: a prefix named `default` (#518)

**Now.** `prefix default <http://u/>` writes `{"prefix": {"default": ...}}`,
which reads back as the default namespace. Every other format round-trips it.

**Change.** The helper from 3.4 renames a registered prefix `default` to a
generated one (`default_1`, following `NamespaceManager`'s renaming) and rewrites
every name using it.

**Tests.** `test_qnames.py`, beside 3.4.

### 3.6 PROV-N reader: `\uXXXX` and `\UXXXXXXXX` escapes (#521)

**Now.** `"café"` fails with "unknown string escape '\u'"; an escape inside
an IRI fails earlier with "unterminated IRI", since `_IRI` excludes `\`.

**Change.** `provn_lexer.py`'s `_unescape_string` decodes `\u` with four hex
digits and `\U` with eight, inside strings (short and long) and IRIs. Escapes are
decoded per token, not before tokenising, so an escaped `"` cannot end a string.
Bad hex, or a code point that is a surrogate or above U+10FFFF, raises
`ProvNSyntaxError` at the escape.

**Tests.** `test_provn_lexer.py`: both forms in each token kind, the error cases
with positions; a round trip in `test_provn_escaping.py`.

### 3.7 Ill-formed typed literals stay literals (#522)

**Now.** `"abc" %% xsd:int` and `xsd:double` reject the whole PROV-N document
(and lenient skips the statement); `"maybe" %% xsd:boolean` stays an opaque
`Literal`; PROV-JSON `{"$": "abc", "type": "xsd:int"}` escapes `deserialize()` as
a bare `ValueError`.

**Change.** One rule for every datatype and reader: a literal with a bad lexical
form stays a `Literal`; a good one converts as today.
`ProvRecord._auto_literal_conversion` (`records.py:867`) catches `ValueError` and
`OverflowError` from `parse_xsd_types` and returns the literal. `parse_xsd_types`
and `XSD_DATATYPE_PARSERS` are public and stay unchanged. The comment in
`provn_parser.py:380-383` that cites `int("abc")` is updated.

The PROV-O reader parses `xsd:dateTime`, `xsd:gYear` and `xsd:gYearMonth`
itself and raised `ValueError` for an ill-formed one; it hands the text to the
model as a `Literal` instead.

**Tests.** Appended to the shared `attribute_values.py` corpus (append only:
some tests index it), so every format round-trips an ill-formed `xsd:int`,
`xsd:double` and `xsd:dateTime`. The ill-formed `xsd:boolean` has its own
round-trip test, because rdflib rewrites it as `false` in both PROV-O directions
(#575), and PROV-O is an expected failure there.

### 3.8 PROV-N writer escapes `xsd:anyURI` values (#526, first half)

**Now.** An `xsd:anyURI` value containing `"` is written unescaped, and the
output fails to read back.

**Change.** `Identifier.provn_representation` (`identifier.py:246-248`) escapes
through the same routine as string literals
(`_ensure_multiline_string_triple_quoted`, `records.py:342-356`), imported inside
the function to avoid the import cycle. Keeping `xsd:anyURI` as a `Literal`
rather than an `Identifier` is a type change and stays with #482 in 3.3.0; the
issue moves there once this lands.

**Tests.** `test_provn_escaping.py`: `"` and `\` in an anyURI round-trip; an
escaping value appended to `attribute_values.py`.

### 3.9 PROV-JSON `hadMember` arrays keep their identifier and attributes (#530)

**Now.** A `hadMember` with `"prov:entity": [a, b, c]`, an identifier and an
attribute reads as one identified membership with the attribute and two bare
ones.

**Change.** The fan-out loop at the end of `_decode_record_instance`
(`provjson.py:510-515`) builds every membership with
`bundle.new_record(rec_type, rec_id, {...}, other_attributes)`.

**PROV-JSONLD changes too (decided 2026-10-17).** The PROV-JSONLD reader copies
the attributes to every member but, since 3.2.1 (5cf52da, PR #468), drops the
`@id` with a `ProvWarning` when a Membership lists more than one member. The
only reason recorded is that `unified()` raised on records sharing the
identifier, which the `unified()` change below removes. The submission allows
the `@id` (sections 4.18 and 6) and maps the statement to one
`provext:Membership` node (5.19), so the identifier belongs to every member.
Both readers build the records through one helper, which also settles the
"shared Membership fan-out" item deferred from 3.2.1.

**`unified()` must change in the same PR.** Today `unified()` raises
`ProvUnificationError` on two memberships that share an identifier but differ
in their members (the 14 October comment on #530). The JSON reader's output
never hit that, because it kept the identifier on the first member only. Once
every member carries the identifier, a document that unifies today would raise
after the reader fix, so the reader fix on its own would be a new rejection.

The comment proposes the fix that goes with it. PROV-DM gives `hadMember`,
`alternateOf`, `specializationOf` and `mentionOf` no identifier (PROV-N
productions 24 to 26, and PROV-Links for `mentionOf`), so `unified()` leaves
those four kinds out of the merge by identifier. A group that raises today then
passes through unchanged. That accepts more and fits the rule.

One side effect was decided as D10 (outright exclusion). Today two *equal* memberships with the
same identifier merge into one record. With the exclusion, both are kept, so the
record count of `unified()` changes for such a document. No input is rejected.
The alternative is to exclude these kinds only when the group would otherwise
fail to unify, which keeps today's output wherever it exists but makes the rule
harder to state. The recommendation is the plain exclusion, with a changelog
line.

`prov_to_graph` (`graph.py:111`) and `prov_to_dot` (`dot.py:579`) call
`unified()`, so both changes reach them. Two equal memberships that share an
identifier become two edges and two arrows; the changelog line names both
functions. A document that fails to unify today now unifies, so
`prov_to_graph` stops raising on it and `prov_to_dot` stops falling back to the
bundle as asserted. `==` and the writers do not call `unified()`.

**Tests.** `test_json.py`, beside
`test_had_member_multi_entity_hack_survives_attribute_order`, which still passes.
In `test_unification_rules.py`: the comment's PROV-N reproduction unifies
without raising; the same holds for `alternateOf`, `specializationOf` and
`mentionOf`; and the JSON document from 3.9's reproduction unifies both before
and after the reader change.

### 3.10 Non-finite doubles are written in XSD spelling (#550)

**Now.** `float("inf")`, `float("-inf")` and `float("nan")` are written as
`inf`, `-inf` and `nan`, which are outside the `xsd:double` lexical space. The
issue names the PROV-JSON writer (`provjson.py:609`) and the PROV-N writer
(`records.py:387`). The same `repr` spelling is in the PROV-JSONLD writer
(`provjsonld.py:202`), and PROV-XML writes lower case too (both verified); RDF
already writes `-INF` and `NaN` through rdflib. Readers accept `INF`, `-INF`,
`+INF` and `NaN` today and write them back in lower case, so a conforming
document does not survive a round trip.

**Change.** One helper spells a `float` for every writer: `INF`, `-INF` and
`NaN` for the three non-finite values, `repr` otherwise. All four non-RDF
writers use it. Readers are unchanged. They already accept the XSD spellings,
and `"inf" %% xsd:double` keeps reading as a `float`, because `float()` accepts
that spelling and #522's fallback (3.7) never applies (probe on 14f5308). That
is an output correction and fits the rule. #550 gains the `prov-xml` label and a note
that PROV-JSONLD and PROV-XML are in scope.

**Tests.** Appended to `attribute_values.py`: `inf` and `-inf`, so every format
round-trips them through the shared modules. `nan` stays out of the corpus. The
shared `roundtrip` fixture compares whole documents with `==`
(`conftest.py:87`) and has no hook for a single value, and `nan != nan`.
Comparing NaN as equal would change equality, which section 8 keeps for 3.3.0.
A separate test round-trips `nan` through each format and checks the value
read back with `math.isnan`. A writer test asserts the exact spelling of all
three values in PROV-N, PROV-JSON, PROV-JSONLD and PROV-XML.
`strategies.py:91` drops `allow_infinity=False` and keeps `allow_nan=False`,
with a comment that gives the reason.

## 4. Warnings for 3.3.0

Each item says what 3.3.0 will reject, where 3.2.3 warns and any complication.
Unless stated, the warning fires under every PROV-N profile and the input is
read exactly as today.

### 4.1 Language tag that is not BCP 47 (#472)

**Rejects in 3.3.0.** A `Literal` language tag that does not match
`[a-zA-Z]+(-[a-zA-Z0-9]+)*`, from any reader or from code.
**Warns at.** `Literal.__init__` (`records.py:437`), the `if langtag:` branch.
This is a hot constructor; the regex is compiled once and the check runs only
when a tag is given, and the A/B benchmark confirms no regression.
**Note.** The data is mangled today too: the PROV-N writer rewrites `_` to `-`
(`records.py:558`). An empty tag `""` skips the branch; D4 decided that 3.3.0 rejects
it, so 3.2.3 warns on it too (PROV-JSON `"lang": ""` and `Literal(..., langtag="")`). PROV-N
already rejects `"x"@` ("invalid language tag"), because `LANGTAG` needs a letter
after the `@`; PROV-JSON `"lang": ""` reads today as an untagged string. The
3.3.0 rejection covers both, and checks the tag's shape only, not the BCP 47
registry. That matches the pattern above.

### 4.2 Repeated `default` declaration (#508)

**Rejects.** A second `default <...>` in one PROV-N declaration block.
**Warns at.** `_declarations` (`provn_parser.py:296-299`), when `default` is
already set. Today the second one silently wins.

### 4.3 Non-PROV-N whitespace (#509)

**Rejects.** Whitespace other than space, tab, CR and LF between tokens.
**Warns at.** The lexer's skip pattern (`provn_lexer.py:123`, consumed at 233),
through the new lexer channel (2.3). Comments share the regex and are not
scanned.
**Note.** U+1680 is a legal name character, so in 3.3.0 it changes how the text
tokenises rather than being rejected; its warning says that.

### 4.4 Declared prefix that is not a `PN_PREFIX` (#511)

**Rejects.** `prefix _ <...>`, `prefix a/b <...>` and the like.
**Warns at.** `_declarations` (`provn_parser.py:284-293`), full-matching against
the lexer's `_PN_PREFIX`. Such a prefix can never be used in a name, so nothing
else changes.

### 4.5 Timezone offset beyond ±14:00 (#513)

**Rejects.** A PROV-N `DATETIME` with an offset beyond ±14:00.
**Warns at.** `ProvRecord._coerce_attribute_value`, the one place every reader and
code path builds a time, so the PROV-N warning carries the attribute and value but
no line and column. A time slot warns "prov 3.3.0 will reject this"; an
`xsd:dateTime` value of any other attribute warns "prov 3.3.0 will keep it as a
Literal". The PROV-O reader parses `xsd:dateTime` itself, so it hands an
out-of-bound value to the model as a `Literal`. As for 4.15, the warning fires
once per value at assertion: `copy()`, `add_record`, `unified()` and `flattened()`
rebuild records through the same coercion and must not warn again. PR 6 ships
the warning without that guard; PR 10 adds it with the 4.15 mechanism.
**Note.** The shared `parse_xsd_datetime` accepts the same offset from every
other reader and from `"..." %% xsd:dateTime` values. The issue covers PROV-N
only; D5 widens the bound to every reader, at time construction only, and the
3.2.3 warning has the same scope.
**Scope.** The bound applies wherever a
*time* is built: the time argument of a PROV-N relation, PROV-JSON `prov:time`,
and a datetime given in code. It does not apply to a typed attribute value such
as `"2011-11-16T16:05:33+15:00" %% xsd:dateTime`: under 3.7's rule, an
ill-formed literal stays a `Literal` and is not rejected. Today that value
converts to a Python `datetime` with a +15:00 offset in both readers (probe on
797b900). In 3.3.0 it stays a typed `Literal` with its text, which changes the
stored type, and 3.2.3 warns about that. So the check sits at time
construction, not inside the typed-literal path. If `parse_xsd_datetime` serves
both, the typed path falls back to an opaque literal instead of raising.

### 4.6 Unresolvable qualified-name value (#516)

**Rejects.** A PROV-N qualified-name value that does not resolve: `'zz:foo'` with
`zz` undeclared, and `"not a name" %% prov:QUALIFIED_NAME`.
**Warns at.** `_literal` (`provn_parser.py:658` and `681`). For the typed form
the opaque fallback happens in the model, so the parser pre-checks with
`bundle.valid_qualified_name()`.
**Note.** Under D8 (option B, decided 2026-10-14) PROV-JSON and model
assertion follow the same rule: 4.17, 4.19. The PROV-N typed form
`"http://example.org/T" %% prov:QUALIFIED_NAME` compacts to `ex:T` today, as
#551 describes for PROV-JSON. It warns here too, as an undeclared prefix
`http`. Filed as #553 (3.3.0 milestone).
**One warning per value.** The parser hands both forms to the model as an
unresolved literal, and 4.19 checks the same value again at assertion. Without
a rule, one value warns twice, once with a position and once without. Under
D12 the reader owns the warning: readers build records inside a context that
silences the 4.19 check, so 4.19 fires only for values asserted from code.

### 4.7 Attribute named after the statement's own formal (#523)

**Rejects.** `wasGeneratedBy(ex:e, -, -, [prov:activity='ex:a'])` and similar.
**Warns at.** `_expression`, after `new_record` succeeds, so a statement the model rejects records no warning.
The conflicting-value case already raises; the warning covers the two cases
that read today (formal absent, or equal). Not in the model: PROV-JSON relies on
the folding by design.

### 4.8 Local part PROV-N cannot write (#524)

**Rejects.** A local part that PROV-N cannot write without changing the IRI,
from any reader or from code: one holding a character outside `PN_LOCAL`, such
as a space, a control character, `"` or `|`, one starting with a character that
cannot start it, such as U+00B7, or one holding a `%` that two hexadecimal
digits do not follow. This is exactly the set the writer percent-encodes, so
3.3.0 never writes a name it rejects on reading (ruled 2026-10-18 while planning PR 9, for the user to confirm; #524's
"Expected" states the same rule).
**Warns at.** `Namespace.__getitem__` (`identifier.py:468`), which is cached, so
once per name; and direct `QualifiedName(...)` construction
(`identifier.py:271`). Hot path: the A/B benchmark gate applies.
**Note.** The writer already warns for a space or control character at
serialisation time (`identifier.py:166-186`), but a bare `%` is rewritten to
`%25` with no warning; that gains one too. Unpickling also passes through
`__getitem__` and must not warn twice. Nor must a bundle that copies the name
into its own namespace (`unified()`, `flattened()`, `update()`, `prov_to_dot`).

### 4.9 Null attribute value in PROV-JSON (#528)

**Rejects.** `null` as an ordinary attribute value, alone or in an array.
**Warns at.** `_decode_record_instance` (`provjson.py:499-510`). The drop itself
happens in the model's `add_attributes`, which documents skipping `None` and
keeps doing so; the warning is the reader's.

### 4.10 Unknown key in a value object, or a non-string `$` (#529)

**Rejects.** `{"$": "1", "datatype": "xsd:int"}`, `{"$": 1}`, `{"$": null}`.
**Warns at.** `decode_json_representation` (`provjson.py:644-660`). `{"$": null}`
becomes the string `'None'` today; it warns here, not under 4.9.

### 4.11 Formal attribute written as an array (#531)

**Rejects.** A formal attribute written as a JSON array, except `hadMember`'s
members.
**Warns at.** `_decode_formal_attribute` (`provjson.py:565-566`).
**Note.** An empty array raises a bare `IndexError` today. 3.2.3 raises
`ProvJSONException` instead: the input already fails, only the type changes.

### 4.12 Repeated key in a PROV-JSON object (#532, PR #533)

**Rejects.** A repeated key in any PROV-JSON object.
**Warns at.** An `object_pairs_hook` on `ProvJSONSerializer.deserialize`'s
`json.load` (`provjson.py:120`) that runs first and chains to the caller's own
`object_hook` or `object_pairs_hook` (`deserialize_options`, lines 70-79).
**Position.** A reader built for it detects repeated keys at every level:
the namespace table, the sections of a document or bundle, the records of a
section, the attributes of a record, and the members of a value object. It
reports the error once the second value has been read, at the end of the
second occurrence. A repeated bundle key is a separate error that names the
first spelling of the identifier. An `object_pairs_hook` cannot match that
position. `json` calls it once per object after the whole object is parsed,
with no line, column or enclosing record. The 3.2.3 warning names the
repeated key and states that the last value is used. A position or a record
identifier needs a decoder that tracks them, and that waits for 3.3.0.
**PR #533** (external contributor, no milestone, now conflicting with `main`)
implements exactly this hook but raises. Under the rule that is 3.3.0 behaviour.
Proposal: ask the contributor to change the `raise` to a warning and the tests
to `pytest.warns`, keep the PR for 3.2.3 with them credited, and make the
one-line switch to `raise` in 3.3.0. The alternative holds #533 unchanged for
3.3.0 and writes a separate warning PR now. Decision D3.

### 4.13 Undeclared `xsi:` prefix (#510, second half)

**Rejects.** An `xsi:` name with no `prefix xsi` declaration in scope.
**Warns at.** `_resolve` (`provn_parser.py:596-599`) and both qualified-name paths
in `_literal` (`:646`, `:681`). `NamespaceManager` is pre-filled with the
defaults and cannot tell declared from built-in, so the parser tracks which
prefixes each scope declares. Depends on 3.1's writer change, or `prov`'s own
output would warn.
**Note.** Every PROV-N file that `prov` 3.2.2 or earlier wrote with an `xsi:`
name lacks the declaration, so 3.3.0 rejects `prov`'s own past output. Those
files read in 3.2.2 and earlier with the declaration added, because
`_check_reserved_prefix` accepts `xsi` at its predeclared IRI. 3.3.0 rejects
them, with no fallback to the predeclared `xsi` (D13). The how-to (2.5) tells
users to read and write such files again with 3.2.3.

### 4.14 The four `strict`-profile rules (#519)

**Rejects, under `profile="strict"` only.** (a) `default` after a `prefix`;
(b) a statement after a bundle; (c) an identifier (including `-;`) or attribute
block on `alternateOf`, `specializationOf` or `hadMember`; (d) a `prefix prov` or
`prefix xsd` declaration at its predeclared IRI. A different IRI already raises
under every profile (`_check_reserved_prefix`).
**Warns at.** (a) `_declarations` (`provn_parser.py:296`); (b) the `parse()` loop
(`:257-264`); (c) `_expression` (`:478-500`); (d) `_check_reserved_prefix`
(`:303`). No warning under `default` or `lenient`, which keep accepting all four.
**Note.** Two Recommendation examples in the corpus parsed under `strict`
(`prov-n-example-51.provn`, `prov-dm-example-42.provn`, `test_provn_corpus.py:319-328`)
will start warning. The test asserts that warning for each of them and fails on any other.
**Profiles.** Six relaxations separate a strict reading of the PROV-N grammar from a permissive one: bare `mentionOf`, `-` in a required position, `default` after `prefix`, a statement after a bundle, identifiers or attributes on `alternateOf`, `specializationOf`, `hadMember` and `mentionOf`, and a redeclaration of `prov` or `xsd` at the predeclared IRI. #519's four rules are among them. The first two, and `mentionOf` in (c), are not in #519; the 3.3.0 work on #519 should check how `prov`'s `strict` profile treats them. Every other refusal applies under every profile (Q2).

### 4.15 Python attribute values with no PROV form (#482)

**3.3.0.** Converts `Decimal`, `date`, `time`, `UUID`, `timedelta` (as
`xsd:duration`) and `bytes`, `bytearray` and `memoryview` (as
`xsd:base64Binary`) to typed literals (D15), and raises `ProvException` for any
other value with no PROV form. A converted value is stored and read back as a
`Literal`. The readers need no change, because none of them converts these
datatypes back into Python values.
**Warns at.** `ProvRecord._auto_literal_conversion` (`records.py:839-887`), at
the fall-through. Two messages: one for a value 3.3.0 will convert ("value of
ex:when has type datetime.date; prov 3.3.0 will store it as xsd:date") and one
for a value it will reject. The supported types that also reach the
fall-through (int, float, bool, datetime, `Identifier`, `Literal`) are listed
explicitly and never warn. `add_record`, `unified()` and `flattened()` re-run the
conversion on copies; the warning fires once per value at assertion only.
Converting is not a rejection, but it changes the stored type, which callers
comparing values will see, so it is warned about too.
**Ruled 2026-10-18 while planning PR 10.** The check sits in
`_coerce_attribute_value`, on the value `_auto_literal_conversion` returns,
because that method does not know the attribute the message names. A
`ContextVar` set by `copy()`, `add_record()` and `unified()`'s merge marks a
rebuild, and every value warning in the coercion, #513's included, stays silent
during one. Only the listed types convert; a value from another library warns
"will reject this" unless it subclasses a supported type.

### 4.16 `unified()` merging an absent non-expandable formal (#547)

**Rejects in 3.3.0.** `unified()` raises `ProvUnificationError` when two records
with one identifier disagree on a non-expandable position, one absent and one
present. The issue and its follow-up comment fix the positions, from
PROV-CONSTRAINTS Definition 4 and Table 3:

- `prov:plan` on an association: always "none" when absent.
- `prov:activity` on a derivation: always "none" when absent.
- `prov:generation` and `prov:usage` on a derivation: "none" when absent and
  that derivation's activity is also absent; an existential when it is present.

Every other absent formal stays an existential and unifies as today. The six
ProvToolbox corpus cases (`derivation-fail1` to `-fail4`, `association-fail4`
and `-fail5`) then fail to unify. Subtyped derivations (revision, quotation,
primary source) reduce to the derivation base type and follow the same rule.

**Warns at.** `_unify_same_type_group` (`bundle.py:222`). The loop over each
formal position already sees every record's value, so it can tell when it fills
an absent non-expandable value from a present one: that is exactly where 3.3.0
will raise. The warning names the identifier, the attribute and the present
value, and the merge goes ahead as today. The generation and usage case needs
the activity of each record, which the same loop has from the earlier position
in `FORMAL_ATTRIBUTES`. This settles the 3.3.0 plan's open question on whether
the warning is feasible.
**Callers.** `prov_to_graph` and `prov_to_dot` call `unified()`, so the warning
also fires when such a document is rendered, and it must point at the
caller's line through them. In 3.3.0 `prov_to_graph` raises and `prov_to_dot`
catches the error and falls back to the bundle as asserted. Both appear in the
how-to (2.5).

**History.** #253 decided the opposite, and two tests pin it:
`test_absent_formal_attribute_unifies_with_concrete`
(`test_unification_rules.py:65`) and `test_placeholder_vs_concrete_plan_merges`
(`test_unification_constraints.py:279`). Filing #547 with an Expected section
that raises is read here as the answer to D2: #253 is overturned for these
positions. In 3.2.3 both tests stay and assert the warning; in 3.3.0 they assert
the error. The condition on generation and usage is checked per record, in
PROV-DM order: the activity position is unified before generation and usage
are reached. Two more oracles for that case,
`derivation-fail5` and `-fail6`, exist on the ProvToolbox corpus branch that is
not yet tagged; the corpus test adds them once it is. `test_unified_corpus_characterization` gains the warning on the six
files.

### 4.17 Full IRI as a PROV-JSON record key or qualified-name value (#551)

**Rejects in 3.3.0.** A PROV-JSON record key, or a value typed
`prov:QUALIFIED_NAME` or `xsd:QName`, whose text is a full IRI rather than
`prefix:local` with a declared prefix. Today `Namespace._resolve_prefixed_string`
(`namespaces.py`) compacts `http://example.org/e1` to `ex:e1` against any
registered namespace that is a prefix of it, with no message.
**Warns at.** The PROV-JSON reader, before it hands the text to the shared
resolver: record keys in `_decode_record_instance` and qualified-name values in
`decode_json_representation`. The check runs only when the part before the
first `:` is not a declared prefix and the compaction succeeds. The resolver
itself is shared with the model API, where a full IRI stays a documented
convenience, so it does not warn. The PROV-JSONLD reader is out of scope: its
`@id` values are IRIs by definition.
**Decided (D8, option B).** Every unresolvable qualified name is refused, not
only full IRIs. The reader does no IRI detection: it splits at the first `:`
and looks the prefix up, so a full IRI is an undeclared-prefix error that names
the scheme. A declared prefix named `http` still reads `http://example.org/Thing`
as prefix `http`, local part `//example.org/Thing`, as today. This is why input
cannot be special-cased by its text. The same rule covers values typed
`prov:QUALIFIED_NAME` and `xsd:QName`. The #238/#257 lock and
`test_unresolvable_qualified_name_literal_stays_opaque` (`test_json.py:142`)
go in 3.3.0; in 3.2.3 the test asserts the warning. Model assertion (4.19)
closes the round-trip gap, so `prov` can no longer write such a value.

### 4.18 Undeclared datatype prefix in PROV-JSON (#552)

**Rejects in 3.3.0.** A value object whose `type` does not resolve, with or
without a `lang`.
**Warns at.** `decode_json_representation` (`provjson.py`), where
`valid_qualified_name(bundle, datatype_str)` returns `None`. Today the datatype
is dropped and the value reads as a plain string, or as a tagged string when a
`lang` is present; 3.2.3 reads it exactly so and warns, naming the datatype.
When the datatype resolves and a `lang` is present, the existing warning stands.
**Note.** The issue says the same undeclared prefix on a qualified-name value is
already an error in PROV-JSON. It is not yet: such a value stays an opaque
`Literal` today. Under D8 it becomes an error in 3.3.0 alongside this one.

### 4.19 Asserting an unresolvable qualified-name literal (D8)

**Rejects in 3.3.0.** A `Literal` typed `prov:QUALIFIED_NAME` or `xsd:QName`
whose text does not resolve against the bundle's namespaces at assertion. That
covers code, and every reader that passes such a value through the model. The
check sits in the 3.3.0 construction-validation step beside #472 and #524.
**Route.** Resolve at assertion, raise only on failure. `Literal(...,
PROV_QUALIFIEDNAME)` stays public and keeps working when its text resolves,
which matches how `ProvBundle` already resolves prefixed strings for
identifiers. Refusing the constructor outright, as the sibling library does, is
the alternative; it breaks every caller that builds one with a declared prefix.
The observable rule is the same either way.
**Resolution.** Prefix lookup only: split at the first `:` and look the prefix
up, with no IRI compaction, so the model agrees with the readers. A plain
string passed as an identifier (`bundle.entity("http://example.org/e1")`) keeps
its documented compaction; the rule applies only to typed qualified-name
literals.
**Warns at.** `ProvRecord._auto_literal_conversion` (`records.py:851-863`),
where `resolved if resolved is not None else literal` keeps the opaque literal
today. An `xsd:QName` literal that resolves stays a `Literal`, as #168
requires; only the resolution check is new for it. A full-IRI
`prov:QUALIFIED_NAME` literal that compacts today warns too, since 3.3.0 will
refuse it. The warning fires once per value at assertion, as for 4.15. Values
that a reader has already warned about do not warn again here (D12).
**Ruled 2026-10-18 while planning PR 11.** The check sits in
`_coerce_attribute_value`, on the original `Literal`, as 4.15's does. The
reader context is its own `ContextVar`, set once per parse in `ProvNParser.parse`
and once per container in `decode_json_container`. Only the PROV-N and
PROV-JSON readers set it; PROV-JSONLD and RDF rely on this check, and the XML
reader already raises on an undeclared prefix in such a value. The PROV-N reader
checks both `prov:QUALIFIED_NAME` and `xsd:QName` values, and an `xsd:QName` text
with an undeclared `xsi` prefix warns (D13). The PROV-JSON reader also warns when
it drops a formal attribute value or a `hadMember` member that does not resolve
(D8). By the user's choice, the other positions where a reader compacts a full
IRI (identifiers, attribute names, datatypes, formal values, bundle keys) stay
silent in 3.2.3 and are listed for a decision.

### 4.20 Malformed bare time in PROV-JSON (#555)

**Rejects in 3.3.0.** A PROV-JSON `prov:time`, `prov:startTime` or
`prov:endTime` given as a bare string that is not an `xsd:dateTime`, such as
`"prov:time": "not-a-time"` or the bare date `"prov:startTime": "2011-11-16"`.
It reads today and the time is dropped with no warning. The model API already
raises `ProvException` for `time="not-a-time"`, so after 3.3.0 every path
agrees.
**Warns at.** `_decode_formal_attribute` (`provjson.py:~571`), where the parse
fails. 3.3.0 raises `ProvJSONException`, matching what #554 asks for the
value-object form, so both spellings fail the same way.
